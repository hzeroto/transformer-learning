# Transformer 教学设计

根据学习者当前能力，写出可直接学习的教学内容。目标不是让读者记住工作流，
而是能解释：已有系统遇到什么问题，这个机制如何改变计算，为什么这样改，以及付出什么代价。
交付实际讲解与材料，不只交付目录、教学承诺或流程报告。
用户当前明确要求优先于本 skill 的默认做法。

## 按实际教学动作判断是否使用

- 用户明确指定本 skill、要求设计下一课或重写讲义时，使用本 skill。用户只说“继续推进”“下一步”等，而下一步将进入新的连贯知识块、组织新一课的讲解与检查时，也必须先使用本 skill；不能仅凭“继续”二字把请求排除。
- 仅解答当前课的问题、补充局部例子或接着讲当前课尚未讲完的部分，保持自然对话，不重跑备课流程。局部答疑中引入一个必要术语，不等于另开一课；若需要整体重设计，则回到本 skill。
- 进入新知识块时，即使仓库已有同主题讲义，也先按本 skill 核对进度、内容与检查的适配性，再复用或按需更新；不必重写合适的材料、生成重复讲义或重考已通过的内容。

## 读取设计依据

- 先按项目入口完成操作系统、映射仓库根目录与 origin 的身份核验，再完整读取仓库 [AGENTS.md](../../../AGENTS.md)。不从 cwd 或 skill 安装目录猜项目路径；缺少项目入口时先确认仓库。
- 读取 `learning/learner-profile.md`、`learning/roadmap.md`，检查 `learning/map.json` 中相关节点、必要先修与验收标准，以及 `learning/progress.json` 中的实际能力证据。
- 按需读取相关讲义、练习接口与实现；只有状态证据不清时才追查对应的 `learning/records.jsonl`，不要重放全部学习历史。
- 以当前请求和最新能力状态为准，不采用旧讲义中的进度快照。`currentNodeId` 为空不代表从头开始。

## 让机制从具体问题中出现

- 选定一个连贯的知识块，可以覆盖多个节点；顺序服从理解依赖，不按节点数量、日期或预计时长切课。
- 从学习者已有的代码、实验或能立即理解的任务出发。先让读者看见当前计算的限制或管理问题，再命名新工具。例如参数从两份扩到几十份后可能漏更新、漏保存，这比先定义容器类更能解释参数注册的目的。
- “控制尺度”“保留信息”“增加表达能力”只能作总结，不能代替机制解释。指出具体哪个量、哪条路径或哪个行为改变，以及它怎样影响读取、学习、预测或模型状态。
- 区分能力需求与结构选择：反例可证明某个固定仿射变换做不到某个函数，但不能据此声称只有 FFN 能实现它；一个网络训练更方便也不等于删掉某组件就一定不能运行。
- 教材正文不必使用统一的“问题—原理—实现”标题模板，更不需要职业动机或课程规划长篇。让段落自然回答读者紧接着会问的“为什么”“不这么做会怎样”。

## 用对照计算承担解释工作

- 对关键设计选择，优先给出能区分方案的最小对照：尽量保持输入与无关参数相同，只改要解释的机制；给出可观察的差异，然后解释原因。例子应回答为什么选择某方案，不只是把公式代入算一次。
- 选择与当前工程有关的后果：同 shape 但读错信息、loss 下降但漏更新参数、保存恢复丢状态等。是否报错不是正确性的充分判据；不为了戏剧性捏造故障或夸大必然性。
- 需要推导的结论给出推导，数值或 API 行为需要核对时实际运行。有限采样用于观察，不证明期望恒等；同一个随机机制也可能两次得到相同结果。没有实跑不标“实测”，小例子不能证明训练收益或一般等价性。
- 一个连贯例子能承载多步时，沿用对象并逐步解释每步的职责；不为每个运算符换一套符号。不要给学习者重复低价值手算。

## 把严谨性放在读者需要的位置

- 在第一次实际使用对象之前，紧邻说明其数据来源、含义、完整 shape 和轴顺序；省略轴时明确固定的索引及局部向量/矩阵。不要为了列全接口，把尚无用途的大表放在问题之前。
- 新 Python/PyTorch 语法第一次出现就解释，不把记 API 当成能力关卡。机制讲清后再给必要代码片段，核心练习实现仍留给学习者。
- 主线必须保留会改变结论的条件；次要 API 边界和实现契约放到相应小节末尾或实现备忘。不反复插入“尚未验收”等管理说明打断机制解释，也不以顺口为由删掉关键限定。
- 区分“知道连接顺序”“能解释选择”“能实现和排错”。答对 shape 或边界题不能覆盖读者明确提出的动机不清；先修只是尚待某项集成验证时，也不从头重教已会部分。
- 图用来解释难以线性描述的关系，按 [图解要求](references/visuals.md) 制作并检查；简单数值对照可直接用表格。整块流程图应帮助回看已经讲明的选择，不能代替这些选择的解释。

## 少量检查与重写

- 检查只覆盖尚缺的关键证据，题面自包含且不考未教内容。优先预测一个改动的后果、解释一个反例或在综合实现中核验；不要直接把刚展示过的答案换个标题再考一次。
- 用户反馈“只有流程、没有目的”时，重写受影响的叙述顺序与例子，不只添加“为什么”标题或在旧正文前堆几段补丁。此时读取 [教学对照样例](references/teaching-patterns.md)，提炼解释方式，不照搬题材或全部措辞。
- 已通过的小检查保留证据，不因讲义重写而重置或重考。若用户此刻只要教材，不把新检查变成立即必须完成的作业。

## 交付与后续对话

- 默认把可复用讲义放在 `notes/`，先检查并复用同主题材料；随讲义保存所需图解资源。若用户只要聊天内内容或指定位置，遵从其要求。
- 正文面向学习者，核心是解释、例子、图解与代码。节点映射、先修判断和验收目标仅保留必要的简短交接信息，不让备课过程占据正文。
- 交接时明确哪些内容只是准备好了、哪些已经实际讲过。练习设计不能把“讲义已生成”当作“先修已掌握”。
- 课案允许自然对话中补充、跳过已会部分或调整例子，不要求逐段确认。当前课内的续讲不重跑设计流程；转入新知识块时，按上面的触发规则使用本 skill。
- 编排教学不自动修改 `map.json` 的依赖、重排整个路线或更新能力状态。确有地图问题时指出依据与建议；仅准备材料不代表开始学习或掌握。

## 交付前核对

逐项看正文，而不是只检查是否出现了某个标题：

- 读者在遇到新组件之前，能否指出它要处理的具体问题？删掉组件名称后，这段理由是否仍然成立？
- 关键例子是否解释了方案差异及其后果，而不只是展示计算结果？参数/算子的职责是否落到了具体计算上？
- 是否把经验收益说成必然、把随机结果说成每次相同/不同、把数学推导和实际运行混为一谈？
- 对象、公式、代码与图是否一致，局部简化是否明确，数值与链接是否核对？已有实现与组合草图是否分清？
- 已会内容是否被重复测试，进度和工程边界是否喧宾夺主？讲义生成本身不构成掌握证据。
