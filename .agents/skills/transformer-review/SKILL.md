# Transformer 审查验收

判断学习者的作品和解释实际证明了什么，给出准确反馈，并同步有依据的能力变化。
用户当前明确要求优先于本 skill 的默认做法。

## 取得当前任务与证据

- 先按项目入口完成操作系统、映射仓库根目录与 origin 的身份核验，再完整读取仓库 [AGENTS.md](../../../AGENTS.md)。不从 cwd 或 skill 安装目录猜项目路径；缺少项目入口时先确认仓库。
- 读取 `learning/learner-profile.md`，检查知识地图中相关验收标准和 `learning/progress.json` 中的现有证据。按需读取路线、相关练习契约及历史记录，不将旧快照当最新状态。
- 代码提交：明确本次要审查的版本，再检查对应实现、相关变更、调用方和测试。聊天贴出的版本与仓库不同时，按用户指定的提交审查并说明差异，不拿另一版本的通过结果代替。用户贴出的“OK”是线索，不替代对当前版本的审查。
- 概念提交：先确认最近有效的题目目标、对象、shape 和回答对应关系。使用最新明确条件；存在影响判分的歧义就先澄清，不猜旧题，不据此判定能力退步。
- 分清代码由谁完成、教师提供了哪些提示和测试。教师自检、示范或给出的答案不得伪装成学习者独立证据。

## 按请求审查

### 代码 review / 排错

- 按题目契约检查数学、索引、数据可见性、数值稳定、梯度和状态等相关行为；先运行针对当前实现的测试，再按改动风险扩大回归范围。
- 补充诊断应非破坏性，优先使用临时小样例复现。只有用户要求补测试或修改时才持久化对应改动；默认不改核心答案，也不悄悄修好后再宣称通过。
- 给 bug 提供位置、触发条件、预期与实际差异及原因。区分阻塞 bug、未验证范围和可选风格建议，不把契约外要求变成验收门槛。
- 不降低容差、删改测试或跳过失败来制造通过。测试可能有错时独立核验其期望，清楚说明依据；不能只因参考输出不同就认定学习者错。
- 报告实跑命令、实际通过/失败/跳过情况。没有执行时明确是静态审查或结果未复现，不能宣称测试已通过。

### 最终测验 / 概念验收

- 先用已有解释、实现和排错证据覆盖验收标准，只对真正缺失的关键项出少量新检查。
- 每道题重新给出必要定义、已知 shape、固定的索引及待求内容；若形状是考点，提供推导条件而不直接给答案。
- 不考未教的新机制，不以背 API 或重复低价值手算作为通关标准。一份综合作品可为多个节点提供各自证据。
- 无须把所有节点都拆成口试。非阻塞的小缺口保留待验证，在后续集成中自然验证。
- 发现先修未讲或题面含混时，先补说明；“理解了”可继续对话，但单独这句话不构成掌握证明。

## 结论与进度

判定或写入学习状态前，完整读取 [能力证据与上报](references/evidence.md)。
优先回答“是否通过、还差什么”。有充分证据就通关，不为展示严谨继续加题。
指出实际覆盖的能力范围，按现有 reporter 同步，最终只报告真正成功的更新。
没有新证据的重复 review 不机械追加记录；普通小错误和可选改进不自动撤销已经成立的能力。
