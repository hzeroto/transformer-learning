# 能力证据与上报

## 从作品到能力结论

将本次可观察表现与相关节点的 `masteryCriteria` 对照，结合已有证据判断，而不是根据测试总数批量标记。

| 实际观察 | 可以支持 | 不能直接推出 |
|---|---|---|
| 学习者实现通过教师提供的测试 | 所测契约、数值/梯度或性质成立 | 独立设计了测试、所有理论均掌握 |
| 学习者独立解释或构造反例 | 对应机制与边界的理解 | 已完成实现或性能实测 |
| 学习者自行定位、修复并验证错误 | 对应排错能力 | 对所有同类问题均有经验 |
| 教师讲解、参照、图片或演示 | 提供过学习材料 | 学习者已经掌握 |
| CPU 小模型正确 | 该配置的正确性 | GPU 加速、生产服务性能或通用语言能力 |

已给出完整答案后的复述不当作独立推导。获得提示后自行修正仍可作为实现证据，记录帮助程度即可，不要求一切必须零提示完成。
同一份实现可以支持多个节点；每个节点需要各自充分的具体证据。部分理解用 `verify`，不是整组一律通过或一律回退。
题面歧义和 API 名称记错不自动等于概念不懂。确认一个局部缺口时只记录该缺口，不无依据推翻其他能力。

## 写入规则

- 复用仓库现有协议，不新建平行进度库，也不把普通对话写成逐消息日志。
- 正常验收有新证据时，按 `AGENTS.md` 要求上报；用户明确要求只读、不记录或此处是 skill 的模拟测试时，不写真实学习状态。
- 写入前重新检查相关当前状态和最近证据，避免重复提交同一证据，或覆盖另一设备已经更新的结论。仅负责审查的子代理提供证据建议，主流程串行执行上报，避免并发写入。
- 在已核验的真实仓库根目录使用当前 `scripts/report-learning.mjs`；不要直接改进度、事件或生成文件。

```bash
npm run learning:report -- master NODE_ID --evidence '学习者实际做了什么、怎样验证、覆盖什么范围' --note '仍未覆盖的边界（如有）'
npm run learning:report -- verify NODE_ID --evidence '已验证的部分' --note '具体剩余缺口'
```

`NODE_ID` 是占位名，执行前从 map 中解析真实 id；以上不是要全部执行的固定步骤。
证据应简明、可核验，说明相关代码/测试或解释。不要复制整段聊天、题目变更过程或教师心理判断。

## 焦点与结果核对

- `current` 表示实际学习焦点，不表示已掌握，也不因刚生成课案或脚手架就必然切换。
- 当前 reporter 切换 `current` 时会把原 current 设为 `verify` 并更新备注；需要保留具体缺口时，先明确上报原节点的 `verify` 和备注，再设置新焦点。
- 原 current 被上报为掌握后，`currentNodeId` 可以变为空。这不是进度丢失，也不是要求再学一次。
- 不传 `--note` 会保留旧备注；状态变化后旧备注若失效，应给出新的准确备注，不保留“尚未实现”等过时描述。
- 上报会追加记录并生成展示文件；不无条件重试。若返回不确定，先读取状态和事件确认是否已成功，不能再次追加相同记录。
- 查看命令实际结果；课程依赖改动或生成状态可疑时运行 `npm run learning:validate`。该命令会刷新生成文件，不是只读检查。
- 上报失败时区分“验收结论成立”和“尚未同步成功”，不要谎称状态已更新，不用手改生成文件绕过失败。
